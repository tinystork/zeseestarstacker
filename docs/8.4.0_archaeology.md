- ordinary worker full-batch path 8610 repeats pre-increment/process/move/save/count;

  mechanical failure propagation is in scope, Reproject photometry is NOT;

Resume/cumulative nuance (avoid overstating this old defect):
- A reducer returning None does NOT itself update SUM/WHT or the clean source
  ledger: `_combine_batch_result` is bypassed. But sources are moved, committed
  batch counter/count file/metadata advance, and a periodic partial FITS may be
  written with a false batch number. A later successful batch can inherit the
  false counter and ledger/plan gap.
- `_combine_batch_result` has early returns for unavailable/invalid arrays or
  all-zero WHT. It marks checkpoint dirty before SUM/WHT/SUP mutation, updates
  image/exposure/header state, and calls `_checkpoint_commit_batch` at 13027.
- That method ALSO catches checkpoint/MemoryError/general accumulation failures
  and can return normally. Caller must never mistake those returns for commit.
- `_checkpoint_commit_batch` appends `_current_batch_paths`, checks uniqueness,
  assigns the in-memory ledger before durable clean manifest write. Persistence
  failure leaves disk dirty, but in-memory state may already have changed.
- Existing Resume v2 dirty-before-mutation fail-closed crash behavior must remain;
  do not turn a dirty/partially-mutated checkpoint into a fabricated clean state.
- Worker has fatal RuntimeError/Exception handlers setting processing_error,
  stop_processing and ENGINE_PROCESSING_FAILED; use explicit propagation into
  this existing terminal mechanism. Avoid success finalization after failure.

Required implementation: explicit successful commit result/exception; committed
counter after success (and correct manifest count); one shared lifecycle used by
